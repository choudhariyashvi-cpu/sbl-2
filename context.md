# SBL Energy Website — Project Context

Orientation for anyone (human or AI) picking this project up. For commands, see
[README.md](README.md); for verification, see the test runbook (kept locally at
`docs/`, not committed — see the documentation map below).

## What this is

Marketing site for **SBL Energy Limited**, a manufacturer of industrial and
mining explosives based in Nagpur, Maharashtra (incorporated 2002). It exists to
present the product range, publish technical datasheets, and collect enquiries
and job applications.

Audience is business buyers — mining and infrastructure companies — so the
datasheet PDFs are sales collateral, and knowing which ones get downloaded is a
real business signal. That is why download tracking exists at all.

## Architecture

**A static site with a small dynamic edge.** 47 hand-generated HTML pages, plain
CSS, and vanilla JavaScript — no React, no build step for the front end, no
bundler. An Express server sits in front to do the three things static hosting
cannot:

1. Accept the contact and career form submissions and email them out
2. Rate-limit and record PDF downloads
3. Set security headers and issue CSRF tokens

**This rules out static hosting.** An earlier version of this file said the site
was GitHub Pages compatible. That stopped being true once the forms moved to an
API — the pages would still load, but every submission would fail.

### Stack

| Layer | Choice |
|---|---|
| Pages | Static HTML, generated by `_build_pages.py` |
| Styling | Vanilla CSS (`css/styles.css`) |
| Front-end JS | Vanilla (`js/main.js`) — no framework |
| Fonts | Google Fonts: Inter + Space Grotesk |
| Server | Node 18+, Express 4 |
| Mail | Nodemailer via Gmail |
| Storage | SQLite (WAL mode) + CSV |
| Bot defence | Cloudflare Turnstile |

Dependencies are deliberately few: express, cookie-parser, dotenv, isemail,
nodemailer, sqlite3.

## Where the complexity actually lives

Almost all of it is in `server/server.js` (~1,200 lines), and it is heavily
commented — the comments explain *why* each defence exists, which is usually the
part that is hard to reconstruct later. Worth reading before changing anything
there.

The main concepts:

- **Visitor sessions** — a signed `sbl_sid` cookie so one visitor's rate limit
  does not punish everyone on the same browser. Fairness, not security; the
  per-IP layer is what enforces.
- **Two-layer rate limiting** — session budget plus IP budget, on forms, PDFs
  and CSRF issuance alike.
- **CSRF tokens** — validated before Turnstile, but only *spent* once mail is
  sent, so a rejected submission does not strand the visitor.
- **PDF whitelist** — rebuilt from disk every 5 minutes, so adding a datasheet
  needs no restart.
- **Public-directory whitelist** — only four asset folders and root `.html`
  files are served. New files are private until deliberately published.

## Constraints worth knowing before changing anything

**Single instance only.** Rate-limit counters are in-memory `Map`s and the
database is a local file. Running two copies would double every limit and split
the download data. Scale vertically, or move that state to a shared store first.

**The database is in WAL mode.** `downloads.db` alone is not a complete copy —
see the backup note in the README.

**`server/data/` and `server/logs/` are gitignored**, so they are absent from a
fresh clone and the server recreates them empty without complaint. A deploy that
wipes the directory silently loses all tracking history.

**Names are not character-restricted.** Deliberate — real names contain
apostrophes, hyphens and accents. Safety comes from escaping on output
(`escapeHtml`) and stripping newlines from mail headers (`sanitizeEmailHeader`),
not from rejecting input.

## Page generation

`_build_pages.py` (root) is the current generator. The three scripts in `build/`
are an earlier generation of the same idea, kept but no longer edited. If you
touch page templates, confirm which one actually produced the page you are
looking at.
